## Confirmed core findings
- Six PWM outputs and adjacent logical pair aliasing; six persisted defaults; independent tach counters.
- Startup/default request2 updates EEPROM before the calibration live-write gate; current request4 is live-only.
- Calibration starts countdown10, forces six compares255 and captures18 backing words, not12; only12 tach inputs are populated.
- Main MCU-watchdog service does not depend on host traffic arriving, but shares the control loop with USB/peripheral callbacks; a stalled callback can prevent that feed.
- Host keepalive/recovery state, shared dangerous-command counter, persistent OLED/BME280 features and key telemetry branches are consistent with the map. Some details were explicitly not checked by each reviewer; see limitations below.

## Parent-verified issues and corrections

### 1. Concrete decompiler error: EEPROM word return
At flash byte0x3890, generated `eeprom_read_word` returns its address parameter, which is wrong. Assembly0x3890–0x3898 sets X to memory0x0018; the engine at0x38da–0x38f4 loads EEPROM bytes and stores through X at0x38ec. Memory0x18/0x19 aliases CPU R24/R25, the actual return value. The decompiler misses that alias.

Parent directly inspected both the generated file and instructions. Explicit register-storage prototypes did NOT fully solve the alias semantics. The original firmware helper is not shown to be broken; the C representation is.

### 2. Hidden arguments and interrupt masking in pseudocode
The generated byte-update helper0x389c has a no-argument signature, though assembly uses addressR25:R24 and valueR22. Its C also obscures CLI at0x38b6, the interrupt-masked EEPROM strobe and SREG restoration. R1=0 statements can be analysis assumptions, not actual instructions. I2C argument and BME stack alias inference remain imperfect.

Treat relevant C as semantically unreliable until repaired/model-checked; assembly is authoritative. No attempt to rewrite or flash firmware was made.

### 3. Calibration is effective averaging, not a running maximum
Normal publication stores five times one interval's count and clears it. Calibration skips clearing across intermediate ticks, then captures the total over five intervals. For equal intervals and absent loss/overflow, this is on the same scale as five times the interval average, not an independent raw-count unit or a running maximum. Publication pauses during part of calibration; another request13 restarts the countdown.

The capture's read→EEPROM-update→clear sequence permits edges arriving between the read and clear to be discarded. Nested pin-change interrupts and the double PINA read at0x0f46/0x0f4e create additional possible counting races. Parent verified the instruction sequences; actual measurement error has NOT been quantified. No numeric elapsed duration is established without clock/fuse evidence.

### 4. Five-request gate does not protect other EEPROM writers
Request15 at0x2646–0x2656 computes2*(10+index-low) without validating the selector, then updates an EEPROM word. The addressable cells include watchdog configuration and the boot marker. Therefore the repeated-reset/boot-command gate is not a general barrier against modifications to persistent control state.

Parent checked the actual calculation/call and verified address examples arithmetically. No malformed request was issued. This is an input-validation/robustness finding about local USB access, not a demonstrated remote exploit or measured hardware failure.

### 5. Enabled watchdog with zero threshold
At0x27aa–0x27ec, a small nonzero short-timeout input can be divided bythree to zero while selecting enabled mode2. The main unsigned elapsed>=threshold test can then be immediately true. Startup normalization checks the mode range, not all threshold combinations. Extra recovery budget also differs from the ordinary retry stage: a keepalive restores the latter, not necessarily the former.

This is a static invalid-input edge case; no zero-threshold configuration or reset escalation was tested. Physical PC3/PC4 wiring and precise times remain unverified.

### 6. OLED modes and boundaries
The field is an equality-selected mode, not a bitmask. Mode4 draws the request character first, then clears the display and change-only-updates EEPROM200..519 to zero. It is not a flash-style erase to0xff and does not physically rewrite already-zero cells. Mode3 uses a2x2 text footprint: offsets0,+1,+20,+21. At row/column boundaries these can cross rows or text banks; persistence lacks the needed coordinate validation.

Parent checked mode4 comparison/zero-update loop and EEPROM update implementation. Existing exact address formulas in FW3-USB.md identify the neighbouring cells; complete physical display effects were not tested.

## Corrections/limits in Claude's own reports
- The fan review's final statement that duty changes after calibration only on request4 or reboot is too narrow: an accepted request2 after calibration also falls through to live duty. The earlier parts of that review correctly establish this.
- The peripheral reviewer could not find literal4710 in the JSON. It is stored as hex: `artifacts/installed-3.0/restored.json`, JSON pointer `/fans/4/3`, value `6612`; little-endian decoding gives4710. Parent rechecked this. It supports an operating reported tach channel but does not alone settle exact silicon register layout or electrical source.
- AVR-libc and firmware agree on PCMSK4 address0x75; one online Microchip summary says0x74. This remains a documentation/silicon identification question, not a proven dead-Port-E firmware bug.
- Claude's OLED branch address text has a typo; use the actual disassembly and final request catalog, not that malformed range.
- The peripheral continuation did not independently inspect all compensation arithmetic or PSU paths. The watchdog reviewer did not independently verify every PWM guard or boot marker consumer. The fan reviewer did not exhaustively disprove every computed-pointer store alias. No review established real clock/fuses, precise timing, physical connector wiring, full sensor calibration or complete semantic equivalence of C to firmware.
